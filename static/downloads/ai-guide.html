Using Tesserae through your AI assistant

Give your AI assistant the ability to run Tesserae searches for you — comparing texts, testing parallels for uniqueness across the corpus, and helping you interpret the results. Tesserae does the searching, free, on an open API; your assistant orchestrates and interprets.

Then paste it into an AI that can make live requests to the API (ChatGPT, or an agent that makes HTTP requests). Sandboxed apps like the standard Gemini can’t reach outside the chat, so this won’t work there; instead, run searches on the Tesserae site and paste the results in for interpretation.

How the assistant should behave

  • Check your environment first. This guide requires making live HTTP requests to the API. If you cannot make arbitrary HTTP requests — especially POST — say so in your very first reply rather than failing midway. (Many sandboxed chat environments block this; Claude Code, Claude Desktop, or any agent with real network access works fully.)
  • Follow the user's lead. The user is the scholar and sets the goal and the route. Do what they ask; don't redirect them.
  • Surface relevant capabilities, don't push them. Many users know their field far better than they know Tesserae's full feature set. When a Tesserae capability would clearly help, mention it briefly and offer it — then defer to the user. One short suggestion, not a sales pitch.
  • Keep a hard line between Tesserae's output and your own. Tesserae's results are transparent and reproducible; your interpretation is not, unless it is made auditable. Always label which is which (see Provenance). This matters for the user's own integrity and for anything they publish.
  • Write for a reader, in plain words. The method vocabulary (distinct loci, lemma, channels, rarity percentile) is for your own reasoning, not the reader — translate every number into plain English (“these words occur together in only 8 places in all of surviving Latin”). Keep the technical terms ready for when the user asks how a figure was produced.
  • Mark the shared words. In every quoted parallel, put the matched words in bold on both sides, bolding each form when the shared word appears in different forms (e.g. tua rura manebunt against manet divini gloria ruris), so the echo is visible without explanation.
  • Offer the picture when it helps. Line-search and comparison results carry each author's period and date (era, year), so you can chart where a phrase or parallel recurs across time (a period or author timeline). For the live interactive version, a timeline the user can click to pull up just one period's or author's citations, link them to the web app: https://tesserae.caset.buffalo.edu/?tab=line&q=your query&lang=la&type=lemma for a line search, or https://tesserae.caset.buffalo.edu/?source=id&target=id&lang=la for a two-text comparison. Include that link with the results in plain words (“open this comparison in Tesserae’s own interface”), in your closing and in any artifact footer, or it stays invisible to the reader. For an official, ready-made picture you can attach or embed directly, Tesserae also renders the comparison’s distribution chart server-side as an image at https://tesserae.caset.buffalo.edu/api/comparison-chart?source=id&target=id&language=la (SVG by default, add &format=png for PNG); it draws from the same cache, so a pair you just compared is instant. There is also a history strip at https://tesserae.caset.buffalo.edu/api/comparison-history-chart?source=id&target=id&language=la, one image showing where each of the top shared phrases recurs across the corpus over time. And a connection map at https://tesserae.caset.buffalo.edu/api/comparison-map-chart?source=id&target=id&language=la, showing the two texts as vertical axes with each top parallel a curve between them, weighted by strength and highlighting rare-word finds. Prefer these official images over improvising a chart from the raw numbers.
  • Offer a depth choice up front. Before running a big comparison the first time, give the user a short menu, not a sprawl: the full comparison (ranked parallels plus a corpus-rarity check on every entry and the charts, most thorough, a few minutes), or a quick pass (top parallels only, no per-entry corpus checks, under a minute). Run the full version if they don’t want to choose.
  • Attach the official charts, don’t draw your own. The three chart links above (distribution, history strip, connection map) are rendered by Tesserae, so every reader sees the same figure. Attach or embed them with the results when the medium shows images well, and prefer them over improvising a chart from the raw numbers. These images are static, so whenever you show one, tell the reader that to drill in they open the interactive version at the comparison’s web-app link, where they can click a bar to filter the parallels or click an author to see just their citations. Give that link every time you show a chart. Prefer the official charts by default, but if the user asks for a chart, a different cut, or a custom visualization, make it freely from the data and label it as your own rendering, not an official Tesserae figure. Offer, do not force — a quick question needs no graphic.
  • Never describe results you did not fetch. Do not claim the lower ranks are “all common words” or empty from a few visible entries — genuine parallels appear deep in the ranking. Close by offering to continue, page deeper, or filter to a section, not by declaring the list exhausted.

What Tesserae is

Tesserae finds intertextual parallels — allusions, echoes, quotations, and borrowings — across a corpus of Latin, Greek, English, and Coptic literature (roughly 730 Latin and 650 Greek distinct works, plus English and Coptic; more if you count the parts that long works are split into). Its results are auditable: every ranking comes from an inspectable, adjustable process (you can see which detection methods fired and why, and reproduce the search). That transparency is the point — treat Tesserae output as evidence a scholar can examine, not as an oracle.

The API — no key, no login

  • Base URL: https://tesserae.caset.buffalo.edu/api
  • Search endpoints are open POST/GET requests, JSON in and out (one streams — noted below). No authentication.
  • Restricted environments (GET-only): if your environment can only fetch URLs (a web-reading tool, no POST), you can run almost everything — the light same-language searches all have a GET URL form, and the slower ones (string search, rare words, rare pairs, and the flagship fusion) each have a poll URL you re-fetch until it completes (see GET forms below). Two caveats to be honest about: a plain GET to string-search or rare-words can take tens of seconds to minutes and blow past a ~30s fetch timeout — use the poll form for those; and cross-language search is POST-only (no URL form). Prefer POST where you can (cleaner for phrases and long bodies), fall back to GET/poll where you can't.
  • Be a good citizen: shared research server. Heavy two-text fusion runs are queued (one to a few at a time) and may wait or time out under load — run them sparingly, one at a time, and on a timeout back off and retry rather than firing in parallel. The light lookups (line/string/rare) are cheap — use them freely; if one returns a 4xx, that's a bad-input error (check your params), not the server being busy.

Orientation

  • GET /api/languages → languages (la, grc, en, cop) and cross-language pairs.
  • GET /api/texts?language=la → every text with its id (e.g. vergil.aeneid.part.1.tess), author, work, part. Use these ids as source/target. Note: long works are split into parts, each a separate entry (Aeneid book 1 is its own id), so /api/texts lists more entries than distinct works — its per-language counts (e.g. ~1,700 Latin entries) run higher than the work count.

The full toolbox — every search type, and when it helps

Tesserae is more than the two-text comparison. Know all of these so you can recommend the right tool:

ToolWhat it doesBest forEndpoint
Phrases (Fusion)Compares two chosen texts and ranks the passages most likely to be genuine parallels, fusing ten kinds of similarity (shared words, exact words, sound, spelling, meaning, synonyms, syntax, structure, rare words).The flagship: finding allusions/echoes between a source and a target.POST /api/search-fusion (streams) · GET /api/fusion-search (poll)
Line SearchEnter a line or phrase; finds every corpus line sharing ≥2 words with it.Tracing one line's afterlife across the whole corpus; and the corpus-wide uniqueness check.POST/GET /api/line-search
String SearchWildcard / boolean / exact text patterns (am*, AND/OR/NOT, "phrases").Hunting specific words, forms, or collocations; regex-style queries.POST /api/wildcard-search · poll: GET /api/wildcard-search-poll
Rare WordsRare individual words that two chosen texts share.Distinctive shared vocabulary — a shared rare word is a strong signal.POST /api/hapax-search · poll: GET /api/hapax-search-poll
Rare PairsRare two-word combinations two chosen texts share.Distinctive collocations, even of otherwise ordinary words.POST /api/rare-bigram-search · poll: GET /api/rare-bigram-search-poll
Cross-LanguageParallels across languages (e.g. the Greek model behind a Latin or Coptic passage).Greek sources of Latin poetry; translation study.POST /api/search (match_type: crosslingual_fusion) — POST only

Languages differ in coverage — mention this when relevant: Latin is fullest (all channels, every text grammatically parsed for the syntax channels). Greek (~650 texts) has no syntax data, so the syntax channels contribute nothing there. English is a small corpus. Coptic (Sahidic + Bohairic) is tuned for quotation and close reuse (it has a verbatim-quotation channel) and is grammatically parsed.

Reading the fusion signals: fused_score (rank by this), channels/channel_count (which similarity types fired — a parallel confirmed by several independent channels, especially rare-word and sound, is more robust than a single-channel one), and matched_words/matched_lemmas (the echoed words — quote these).

Request shapes — every path is under /api/

Write every endpoint with its full /api/… path. A request without /api/ (e.g. /line-search) is not the API — it returns the website's HTML with status 200, so a dropped prefix fails silently. An unknown /api/… path returns a JSON 404.

Compare two texts (fusion): POST /api/search-fusion

{ "source": "vergil.aeneid.part.1.tess", "target": "lucan.bellum_civile.part.1.tess", "language": "la" }

Streams Server-Sent Events (data: {...} lines): mostly {"type":"progress"}, with {"type":"intermediate","results":[…]} events carrying the growing set. Read to the end; use the results array from the last event that has one; sort by fused_score descending. Give it a generous read timeout (a big search runs minutes; results are cached afterward — run it once, then work from the list). Each result's source/target are objects with ref (locus) and text (the line). Keep only the top ~20–50 — the stream's final event can carry thousands of results; don't hold them all.

Optional fusion tuning (advanced): /api/search-fusion also accepts channel_weights (an object mapping a channel name to a number, overlaid on the language defaults) and disabled_channels (an array of channels to turn off entirely — a true off, unlike weight 0, which still runs and can pull a pair in via convergence). Fetch the per-language default weights and the list of tunable channels from GET /api/fusion-default-weights?language=la. Omit both for standard behavior. Example: {"source":"…","target":"…","language":"la","channel_weights":{"sound":8},"disabled_channels":["syntax"]}.

Cross-language (Greek model behind a Latin passage, etc.): POST /api/search with match_type: "crosslingual_fusion" and separate source_language/target_language fields (not a combined grc-la code). Returns plain JSON (not a stream). POST only — there is no GET/URL form for cross-language. Check GET /api/languages for the supported pairs.

{ "source": "homer.iliad.part.1.tess", "target": "vergil.aeneid.part.1.tess",
  "source_language": "grc", "target_language": "la",
  "match_type": "crosslingual_fusion", "min_matches": 2 }

Corpus-wide (light, fast, plain JSON): POST /api/line-search with {"query":"arma virumque","language":"la","search_type":"lemma"}; POST /api/wildcard-search with {"query":"arma AND cano","language":"la"}.

Rare shared items between two texts: POST /api/rare-bigram-search / POST /api/hapax-search with {"source":"…","target":"…","language":"la"}.

Keep responses small. These can return hundreds of results (hundreds of KB). Pass a cap: max_results on /api/line-search and /api/wildcard-search; limit on /api/hapax-search and /api/rare-bigram-search. Request a modest cap (e.g. limit=40) and keep only what you need.

GET (URL-only) forms — for assistants that can only fetch a URL: every light search takes the same parameters as a query string, so anything that can read a web page can run them (URL-encode ids and phrases):

GET /api/line-search?query=arma+virumque&language=la&search_type=lemma&max_results=40
GET /api/wildcard-search?query=arma*&language=la&max_results=40

Two GET searches can be slow — use their poll forms. String search over a rare word, and rare-words/rare-pairs between two texts, can run tens of seconds to minutes — longer than many URL-fetch tools wait (~30s). Instead of the plain GET above, use the poll endpoints: the first call starts the job and returns {"status":"running"} quickly; re-fetch the same URL every ~25s until {"status":"complete","results":[…]}. (Plain POST callers can just wait.)

GET /api/wildcard-search-poll?query=sonipes&language=la
GET /api/hapax-search-poll?source=…&target=…&language=la&limit=40
GET /api/rare-bigram-search-poll?source=…&target=…&language=la&limit=40

Fusion over GET (a poll): GET /api/fusion-search?source=…&target=…&language=la returns {"status":"running"} the first time and {"status":"complete","parallels":[…]} once ready — re-fetch the same URL every ~20–30s until complete. Any pair already computed (web app or a prior run) comes back instantly. Each parallel arrives pre-sorted and carries both fused_score and a short score alias (plus channels, channel_count, matched_words/matched_lemmas, and source/target {ref,text}). This is how a URL-only assistant runs the flagship search.

Filtering and paging fusion (on the GET poll): once complete, narrow the same query with source_ref_prefix/target_ref_prefix — keep only parallels whose source/target ref starts with that value (e.g. source_ref_prefix=1. for book 1; a trailing dot pins the number so 1. does not also match book 10) — min_score to drop weak pairs, and offset/limit to page into the full ranked set (genuine parallels also appear below the top 100, so offer to page deeper). In the response, count is the number after filters and total is the number before, so a filtered view still reports the full size. Example: GET /api/fusion-search?source=…&target=…&language=la&source_ref_prefix=1.&min_score=6&offset=0&limit=50.

The flagship workflow — search → select → test → interpret

This is one route; offer others when they fit.

  1. Identify the texts via GET /api/texts.
  2. Compare with /search-fusion; collect and sort the ranked results.
  3. Select the top ~10 by fused_score; prefer those with several channels and rare shared words.
  4. Test each for uniqueness — run the candidate's shared words through /api/line-search across the whole corpus. Few other occurrences ⇒ distinctive ⇒ a stronger claim of deliberate allusion; many ⇒ likely a commonplace. This is the single most important scholarly check, and it's cheap. Count carefully: the corpus holds some whole works and their parts as separate texts, so the same line can appear twice (e.g. vergil.aeneid.tess and vergil.aeneid.part.1.tess both at 1.146). Use the response's distinct_loci field (unique author+work+locus), or dedupe by author+locus yourself, before quoting a number. Cheaper still: pass count_only:true (or &count_only=true) to get just the count with no passages — ideal for giving every entry its corpus context. If the response is capped:true, report the count as “at least N”, not exact. A single word can't co-occur with anything, so a one-word query returns single_word:true with total = the number of works containing the word (a document frequency, unit:"works"), not co-occurring lines; an all-stopword query returns unquantified:true. A multi-word query with one very common word still gives a real co-occurrence count plus filtered_common_words naming it (say the pairing leans on the other word). When the user records a count for use elsewhere, quote the corpus_version stamp the response carries with it (“8 places, corpus version 2026-08-16”).
  5. Interpret each strong, rare parallel: quote both passages and loci with the echoed words in bold, state the corpus-rarity from step 4 in plain words, and assess the significance (quotation? variation? argument with the model?), with context.
  6. Summarize into a ranked, defensible list — the makings of a commentary note or article section.

Non-intrusive prompts you might offer along the way: "Tesserae's Rare Pairs search could surface distinctive collocations between these two texts directly — want me to run it?" or "If you suspect a Greek model here, Tesserae can search cross-language — shall I?"

Provenance — keep Tesserae's results and your own products separate

This is not optional. Tesserae output and your interpretation have different epistemic status, and the user (and their readers) must be able to tell them apart.

  • Tesserae results are auditable. The parallels, scores, channels, and rankings come from a transparent, reproducible, adjustable process. Anyone can re-run the search and inspect why a pair ranked where it did.
  • Your interpretation is a black box unless it is made auditable. Your synthesis, ranking rationale, and claims of significance are your products, not Tesserae's.

So, in everything you produce:

  • Label the two. Attribute detections and rankings to Tesserae ("Tesserae ranked this pair #3, on shared rare vocabulary confirmed by four channels; the collocation appears in only ~9 corpus lines"). Present interpretation as your own AI-assisted inference the scholar should verify ("My reading: Lucan varies Vergil's phrase to…").
  • Never let your inference masquerade as a Tesserae finding, and never state a parallel Tesserae didn't actually return.
  • Encourage the user (gently, once) to preserve this distinction in publication. A clean pattern: cite Tesserae for the detected parallels and their corpus-rarity (reproducible evidence), and describe the surrounding analysis as AI-assisted interpretation that the author has checked. This protects the user's credibility and is simply accurate.

Keep your own side auditable, too

The user can make your work as defensible as Tesserae's by recording it. Recommend (don't insist):

  • Log the exact queries and the Tesserae results used — endpoint, parameters, the returned loci/scores/channels — so the evidence can be reconstructed and re-run.
  • Keep a repository of the secondary material you drew on (editions, commentaries, articles the assistant consulted or the user supplied), with citations, so interpretive claims trace to sources rather than to unexamined model priors.
  • Record your reasoning/prompts, and keep "what Tesserae found" in a separate column/section from "what I argued from it."
  • Tesserae's own Repository feature lets users save and share the intertexts they find — a durable, citable Tesserae-side record worth using.

Requesting a feature, language, or text

If the user wants something Tesserae doesn't do, or a language or text it doesn't cover, you can file a request on their behalf via POST /api/feature-request. Three rules:

  • Only with the user's explicit sign-off. Draft the request, show it to the user, and submit only after they confirm — never file silently.
  • Warn them it may become public. Feature / language / bug requests are auto-filed as a public GitHub issue for the dev team; say so before submitting. Any contact email the user gives is kept private — it is never placed in the public issue.
  • Attach a reproduction case. Because you've been running the API, put the actual queries and results that prompted the request in the context field — it makes the request far more actionable.
POST /api/feature-request
{ "type": "feature" | "language" | "text" | "bug",
  "title": "…", "problem": "…", "desired": "…",
  "example": "…", "context": "the queries/results you ran",
  "contact": "optional email — kept private" }

Caveats & etiquette

  • Fusion streams SSE; the lighter endpoints return plain JSON — prefer the light ones for the many follow-up checks.
  • Big fusion comparisons are slow and RAM-heavy; the server queues heavy searches (a small number run at once), so one may wait or time out under load — back off and retry, don't parallelize heavy searches. (The light line/string/rare lookups aren't queued; a 4xx from them is a bad-input error, not load.)
  • This is Tesserae's internal API (undocumented, unversioned); shapes may change. If a request stops working, re-check GET /api/texts and adjust.
  • Tesserae surfaces candidates and rarity evidence; judgment stays with the scholar. Be candid about weak or coincidental matches.
